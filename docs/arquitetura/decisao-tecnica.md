# Decisão técnica inicial — app prioritário no smartphone

**11/10/2026. Estado: incremento0.3.0; V1 ainda não liberada.**

Atualização: IndexedDB2/fila, cliente Supabase/Auth com link PKCE (template Free padrão), CAS/recibos, conflito conservador e recuperação independente implementados. Migração aplicada e ensaio SQL/RLS/rollback comprovados no projeto Free de teste `azqlukwlcotyhildfvwt`; autenticação/recuperação real pela UI e S23 ainda pendentes. `protocolo-sync.md` é a decisão executável atual; os parágrafos sobre ausência de código remoto abaixo registram o ponto de partida. Git local iniciado. Rollback deverá usar build compatível com IndexedDB2/protocolo1; não voltar destrutivamente ao esquema local1.

Vytor aprovou a direção visual do protótipo v0.2, estabeleceu o smartphone como aparelho principal e escolheu uso em um aparelho com escrita offline e backup exportável. O código inicial em `C:\opscon\app` adota aplicação web instalável (PWA), sem dependências externas em tempo de execução, com dados guardados em IndexedDB no próprio navegador. O service worker guarda somente os arquivos do aplicativo para permitir abrir a interface sem conexão; os registros são gravados em IndexedDB. Não há servidor de dados nem sincronização automática.

**Decisão esclarecida em 11/10/2026:** Vytor precisa recuperar os dados ao entrar em outro telefone após perda do primeiro. O IndexedDB e o backup manual atuais são insuficientes para isso. A V1 deverá manter escrita offline local e sincronizar automaticamente com banco remoto; Supabase é o candidato recomendado. PWA versus APK trata da distribuição e não resolve, sozinho, a persistência. Antes de dados reais, implementar conta recuperável, autorização por usuário/RLS, fila local durável, reenvio idempotente, conflitos, migrações, indicação de pendências e ensaio de recuperação em aparelho limpo. Nenhum projeto remoto foi criado até aqui.

O domínio está separado da interface. Comandos geram novos snapshots validados, em centavos inteiros e com revisão monotônica. Escritas financeiras exigem chave de idempotência. O IndexedDB salva o snapshot em uma transação e confere a revisão para impedir que uma aba antiga substitua alterações recentes. Compra, parcelas e vínculos são uma operação de domínio; Mercado cria uma compra única no fechamento; pagamento só é registrado com ação explícita. A interface usa as mesmas operações e não altera totais financeiros por conta própria.

Backup JSON inclui registros, relações, histórico e chaves de operação. A importação valida o pacote antes de oferecer a substituição; a restauração é transacional e confere a revisão atual. Hoje esse arquivo precisa ser guardado fora do aparelho: limpar os dados do navegador, trocar de origem/endereço ou perder o telefone pode remover a cópia local. Na arquitetura final, o banco remoto permitirá recuperação após login em outro telefone, mas operações locais ainda pendentes de envio não poderão ser recuperadas se o aparelho for perdido antes da sincronização. O app deve mostrar isso claramente. Backup independente continua necessário para recuperar exclusão/corrupção já sincronizada. Hospedagem HTTPS, instalação e recuperação real ainda fazem parte do gate de publicação.

O acesso inicial fica sob a proteção do telefone e do navegador. Ainda faltam decisão e validação de proteção adicional apropriada para dados pessoais, além de correção/estorno, faturas, orçamentos, reservas, recorrências, CSV, anexos, acessibilidade medida e a matriz completa CA-01–CA-22. Nenhum desses itens é declarado entregue pela fundação. MCP da Berenice permanece na entrega D posterior.

Para evoluir sem recriar os dados, mudanças de esquema exigirão migrações versionadas e ensaio de restauração. O modelo atual usa `schemaVersion: 1`; pacotes de outra versão são rejeitados explicitamente. A publicação só ocorre após validação da V1 completa e ensaio no smartphone escolhido.
